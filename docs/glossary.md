# Glossary

Terms used in Data Director, in alphabetical order.

| Term | Meaning |
|---|---|
| A2A | Agent2Agent, an open protocol for one agent service to call another over HTTP. Each service publishes an agent card describing itself, and callers send it messages using JSON-RPC. The harness uses A2A in both directions: callers reach the harness over it, and the harness reaches each agent over it. See [Transport and tracing](specs/transport.md) and [Agents](specs/agents.md). |
| Agent | A program that takes one input and returns one result. In the Blueprint these are the Data Director's sub-agents. Each declares what it reads, what it returns and its grounding mode in an `AgentSpec`. Each runs as its own service and is reached over A2A. See [`../../agents/README.md`](../agents/README.md). |
| Agent card | The JSON document an A2A service publishes at `/.well-known/agent-card.json`. A Data Director agent's card carries its `AgentSpec` in an extension. See [`registry.md`](../harness/docs/registry.md). |
| Agent Skill | A packaged procedure written for a model to follow, such as choosing a licence. A persona loads a Skill as pinned text in its system prompt, never with scripts. See [Agents](specs/agents.md#tools-mcp-servers-and-agent-skills). |
| Canonicalisation | A fixed, named way of turning a record into bytes before hashing it, so the same record always gives the same hash. See [`grounding.md`](../harness/docs/grounding.md). |
| Conductor | The function that runs an agent and applies every check. See [`conductor.md`](../harness/docs/conductor.md). |
| Conformance report | `CONFORMANCE.md`, generated from the test results and the review record. For each requirement it gives a test verdict and, where the requirement needs one, a review verdict. See [`conformance.md`](conformance.md). |
| Content hash | A short fingerprint of a record's content when it was read. If the content changes, the hash changes. See [`grounding.md`](../harness/docs/grounding.md#source-ids-and-content-hashes). |
| Data steward | The Blueprint's *data support professional*: a person who supports researchers with their data, and who owns the deployment's policy. The profile names each steward in a team. A steward sees a researcher's project only when the profile's visibility allows, every look is recorded, and a steward proposes rather than decides. See [Data stewards](specs/stewardship.md) and the [Data Steward's Guide](guide/steward-guide/index.md). |
| Deployment role | A role a person holds in a whole deployment, named by its profile: researcher, data steward or administrator. It is separate from project membership and never makes anyone a member. See [Data stewards](specs/stewardship.md). |
| Deposit package | What the loop ends with: the project rendered by a packager into one format, holding no data files. The default is a zip file that is an RO-Crate of the dataset, holding the approved documents, the file inventory, the validation report and the audit trail; every other format holds it, travels with it or names it. A person uploads a package, with the files, to the chosen repository, or a deposit transport sends it. See [Deposit](specs/deposit.md). |
| Deposit transport | How a package or a rendered record reaches a repository: a platform's API connector, SWORD v2, or a person uploading by hand (the manual transport). Chosen apart from the package's format. See [Deposit](specs/deposit.md#packagers-and-transports). |
| Disclosure | What a project's approved documents owe to generative AI, read from the project's record: for each, whether a model drafted it, which model and when, whether a person changed it, and who approved it. It is given as a statement a researcher can cite and as a PROV-O graph. See [Disclosure](specs/disclosure.md). |
| Envelope | The response to one request: the outcome, the payload if any, the evidence and the telemetry. See [`contract.md`](contract.md). |
| Escalation | A record in a project's log that hands a matter to a steward team, raised by the researcher or confirmed by them from an agent's offer, with a state such as open, taken or resolved. See [Data stewards](specs/stewardship.md). |
| Evidence | The list of source records an envelope rests on, each with a content hash. |
| Grounding | Tying an agent's output to the sources it actually read during the run, so that it cannot present something it made up. See [`grounding.md`](../harness/docs/grounding.md). |
| Grounding linter | The check applied after every run. It compares the sources a result names with what the trace shows the agent did, and withholds the result if they disagree. Also called the grounding check. See [`grounding.md`](../harness/docs/grounding.md). |
| Grounding mode | What an agent's output may rest on, declared by each agent: `retrieval` (records it fetched), `input_only` (only its input, possibly with a model) or `none` (only its input, with no model). See [`grounding.md#grounding-modes`](../harness/docs/grounding.md#grounding-modes). |
| Mandatory review | A review the Blueprint requires before a step may go on, such as a policy referral or confirming ethics approval before deposit. The step stays stopped until its reviewer acts. See [Data stewards](specs/stewardship.md). |
| MCP server | A service that offers tools over the Model Context Protocol. A persona uses one as a source, reached only through the tool gateway. See [Agents](specs/agents.md#tools-mcp-servers-and-agent-skills). |
| OpenTelemetry | A widely used open standard for recording what software does while it runs. The harness uses it for traces. |
| Outcome | What happened in a run: `succeeded`, `abstained`, `referred`, `failed` or `suspended`. See [`contract.md`](contract.md). |
| Packager | What renders a project into a deposit package in one format, such as an RO-Crate zip or a BagIt bag, from a valid validation report. See [Deposit](specs/deposit.md#packagers-and-transports). |
| Pause | A steward's hold on a project: no consequential step runs in it until a steward lifts the pause. It never lapses on its own. See [Data stewards](specs/stewardship.md). |
| Payload | The agent's result, present only when the outcome is `succeeded`. |
| Policy profile | A YAML file in `profiles/` that says which agents an institution enables, which action class each is assigned, and which classes need approval. The deployment chooses it; a request cannot. |
| Problem Details | The RFC 9457 format used to describe a `failed` or `suspended` outcome. |
| Process Run Crate | An RO-Crate provenance record of one run: which agent ran, for whom, on what input, and what it produced. It is written after the run and is not passed between agents. See [Contract](specs/contract.md). |
| Project member, project owner | A person who shares a project: they can read everything in it, run agents in it and add to any of its conversations. An owner can also add and remove members and approve or reject document versions. A project always has at least one owner. Membership is recorded in the project's log, and is separate from deployment roles such as data steward. See [Projects](specs/projects.md). |
| Project fact | Something a person decided about a project: a funder, a repository a funder or institution requires, whether a file is deposited, whether sensitive data may be published and how, or the licence. A check agent may propose one; it becomes a fact only when a person confirms, changes or states it, and every drafter and orchestrator in the project is then given it. See [Projects](specs/projects.md). |
| Project document | A metadata record, README, data dictionary or other document of a project, returned by an agent as a `Document` payload. Each draft, regeneration and edit by a person is a version, and each version is proposed, approved or rejected on its own. See [Projects](specs/projects.md); how a person decides is [Projects](specs/projects.md). |
| Provenance graph | A project's whole history as one PROV-O graph, read from its log and its runs: every event, run, delegation, model call, retrieval, refusal and decision, each attributed to the person or agent that acted and, for an agent, the person it acted for. Content such as prompts and messages is named by digest, not carried. See [Provenance](specs/provenance.md). |
| Question | Something a drafter asks the researcher because it cannot be inferred, such as a field's definition or unit, carried with the draft version and tied to the gap it fills. A person's recorded answer is marked `supplied` when the document is regenerated. See [Drafting documents](specs/drafting.md). |
| Registry | The harness's list of agents it can call, built at start-up from `agents.yaml` and each agent's card. See [`registry.md`](../harness/docs/registry.md). |
| Requirement set | A YAML file of the deployment's that says what a deposit must or should have. A standard's set covers any record in one metadata standard, such as DataCite; a repository override adds what one repository asks, such as its form's fields and the licences it offers. The harness validates a project against the merged requirements of the repository the researcher chose. See [Deposit](specs/deposit.md). |
| Review record | `reviews.yaml`: the human reviews of requirements that a test cannot settle, one entry per review, each naming the reviewer and the commit reviewed. See [`conformance.md`](conformance.md#recording-a-review). |
| Span, trace | A trace is a timed record of one run, in the OpenTelemetry format, written by the harness rather than the agent. It is made of spans, one per step, such as fetching a record or calling a model. Spans nest inside one span for the whole run, forming a span tree. See [`grounding.md#traces-and-spans`](../harness/docs/grounding.md#traces-and-spans). |
| Tool gateway | The harness's one MCP endpoint facing agents. It forwards a persona's tool calls to the MCP servers the deployment lists and the profile grants, and the conductor records each record returned. See [Evidence and grounding](specs/grounding.md). |
| Unavailable agent | An agent listed in `agents.yaml` whose card could not be read or was rejected. It is shown with the reason and cannot be run. See [`registry.md`](../harness/docs/registry.md#when-something-is-wrong). |
| Viewer | The read-only browser pages in `viewer/` (Chat, Inspect and Agents) for trying agents and inspecting envelopes. Formerly called the shell. |
