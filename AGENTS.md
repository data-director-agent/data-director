# Data Director

## Purpose

A reference implementation of the RDA [Data Director Agentic AI Blueprint](https://www.rd-alliance.org/groups/data-director-agentic-ai-blueprint/outputs/data-director-agentic-ai-tool-blueprint/), officially adopted by the RDA and published at <https://doi.org/10.15497/RDA00157>.

## Working here

- Prototype and exploratory agents live in `agents/<name>/` like any other agent, marked as alpha
  by their `pyproject.toml` version (`agents/README.md`) rather than kept in a separate
  non-authoritative tree.
- `app/` is the Data Director app that people use (alpha, `app/README.md`). It must not depend on
  `workbench/`, which is for development only. It runs agents through the harness's conductor,
  with its own configuration in `app/config/`. Its browser shell (`app/web`, React and
  TypeScript, [The app](docs/specs/app.md)) is drawn from each agent's manifest and names no agent; it renders the
  harness's decisions and holds no policy. `docs/ui/best-practices.md` is its design input.
- The repository root is a uv workspace. `harness/` (`dd_harness`) governs agents against one
  contract: the conductor, policy gate, input check, grounding linter, source check, run store and
  provenance, with an A2A way in (`harness/README.md`, [System and boundaries](docs/specs/system.md)), and its test kit
  `dd_harness.testing`. It depends only on `sdk/` and must not import the workbench, the app or an
  agent. `workbench/` is the development way in to
  the harness (see below). `agents/` holds one package and one A2A service per agent
  (`agents/README.md`). `sdk/` is what agents and the harness share: the contract, evidence, span
  helpers and the agent server. `inventory/` is `dd-inventory`, the command a researcher runs
  where their data live to describe a dataset's files ([Projects](docs/specs/projects.md)); it depends on no other member.
  Tooling config is in the root `pyproject.toml`.
- Each workspace member keeps to its own directory: it imports only what it declares (tests
  from its own `dev` group) and reads no path outside itself. [System and boundaries](docs/specs/system.md) says why, and what may
  live in other repositories of the organisation.
- `docs/blueprint/` is the published Blueprint v1.0 reproduced verbatim (RDA, CC BY 4.0,
  <https://doi.org/10.15497/RDA00157>), one file per chapter; `README.md` there has the contents.
  Read the chapter you need: the requirements are in `07-functional-specification.md`, each with an
  anchor (`#r3`, `#c5`). Requirements are cited by ID (`R3`, `R3.1`, …) throughout the repo. Treat it
  as read-only external material, not project prose to improve: the files are generated by
  `scripts/blueprint/convert.py` and checked against the PDF by `scripts/blueprint/check_text.py`.

## The workbench

`workbench/` is a test bed for the engineers and testers who write Data Director sub-agents. It
is not the reference implementation itself, and it contains neither agent code nor governance
code. Through the harness, it calls each agent over A2A, checks that the agent kept to the
contract, and records every run so that a person can inspect what the agent did and why.

- `src/workbench/`: the `workbench` CLI, the AG-UI transport, evaluation (`evaluation.py`) and
  `config.py`, the development configuration it supplies to the harness. The conductor itself,
  which alone fills identifiers, timestamps and lineage, is in `harness/src/dd_harness/`.
- `agents.yaml`: the registry of agent URLs. `profiles/` holds institutional profiles (what an
  instance may do), `sources.yaml` the pinned source copies, and `samples/` example inputs.
- `viewer/`: the browser UI served by `workbench serve`, with an Inspect page and a Chat page.
- `docs/`: `architecture.md` is the overview and `walkthrough.md` follows one run.

Documents are kept with what they describe. `harness/docs/` describes the conductor, grounding
and the registry. The repository-level `docs/` holds what governs every package: the system
overview (`architecture.md`), the specifications in `docs/specs/`, the contract, the glossary,
the requirements register (`requirements.yaml`) and the review record (`reviews.yaml`).

A specification states how one part is meant to work today and why; `docs/specs/README.md` says
what belongs in one. A change to the design changes its spec in the same pull request, edited to
say what is now true rather than amended. Changing a fixed format (schema, `dd.*` trace
attributes, evidence canonicalisation, outcome vocabulary) always changes a spec. `CONFORMANCE.md`, at the root, is
generated by `scripts/conformance_report.py`; do not edit it by hand.

Read `workbench/AGENTS.md` before changing anything here or in `harness/`.

## Committing

Every commit must be signed off under the Developer Certificate of Origin — `git commit -s`.
Unsigned commits are rejected at review.

## Issues and labels

The kind of an issue is its GitHub issue type (Task, Bug or Feature), not a label; an umbrella
issue is a parent with sub-issues. Labels say where and what about:

- `area: …` — the part touched: `sdk`, `harness`, `workbench`, `app`, `agents`, `docs`, `ci`.
  One or more per issue.
- Themes: `blueprint` (review or conformance against the Blueprint), `security`, `evaluation`,
  `accessibility`, and `needs spec` for a change to a fixed format.
- `good first issue`, `help wanted` and `blocked` (waiting on something outside the project).

Pull requests take no labels by hand ([Pull requests](#pull-requests)).

## Pull requests

Read this before you open a pull request, whether with `create_pull_request`, `gh` or any other
route. A wrong title fails the **Names** check, and the title is yours to set: it is not derived
from the commits or the branch.

- **Title.** Pull requests are squash-merged and release-please reads the title as the commit
  subject, so it is a Conventional Commit: `type(scope)!: summary`. `type` is one of `build`,
  `chore`, `ci`, `docs`, `feat`, `fix`, `perf`, `refactor`, `revert`, `style`, `test`. The summary
  starts with a lower-case word, has no closing full stop, and the whole title is at most 90
  characters. `feat(app): register every in-tree agent` is right; `Add approved metadata record
  support to draft requests` is not (no type, capitalised) and fails the **Names** check. Pick the
  type from the change (`feat` for new behaviour, `fix`, `docs`, `ci`, …) and the scope from the
  part touched (`app`, `harness`, `sdk`, `workbench`, `agents`, `docs`, …); add `!` for a breaking
  change.
- **Branch.** Lower-case words joined by hyphens, optionally grouped with slashes (`ci-faster`),
  at most 60 characters. A branch the environment assigns you (`claude/…`) already passes; keep it.
- **Check before you open it**, and again if you edit the title afterwards:
  `python3 scripts/check_names.py --title "…" --branch "$(git branch --show-current)"`. No output
  and exit 0 means it will pass. `.github/workflows/names.yml` runs the same script, on every
  push and every title edit, so a wrong title is fixed by editing it (no new commit).
- **Labels.** None by hand: the Conventional Commit title carries kind and scope.
  `dependencies`, `python:uv`, `javascript` and `autorelease: …` are applied by Dependabot and
  release-please; leave them alone.
- **Project status** (`.github/workflows/project-status.yml`) puts the pull request on the
  project board when it is opened or marked ready for review. It uses the repository secret
  `PROJECT_TOKEN`; when that is unset the job fails with "To use GitHub CLI in a GitHub Actions
  workflow, set the GH_TOKEN environment variable". That failure comes from repository settings
  and not from your change, so do not edit the workflow or the pull request to chase it. It does not
  re-run on title edits or pushes. Tell the user that the organisation owner must set
  `PROJECT_TOKEN` (the setup is in the workflow's header comment) and leave it at that.

## Keeping the board accurate

Work is tracked on the organisation's **Data Director** project board
(<https://github.com/orgs/data-director-agent/projects/1>). The issue is the unit of work, and the
board is only as truthful as the issues and pull requests behind it. How the board is meant to be
used, including the definitions of ready and done, is in the organisation's
[PLANNING.md](https://github.com/data-director-agent/.github/blob/main/PLANNING.md); read it before
changing how you treat an issue. Update the issue as the work happens, in the same session, not at
the end or "later": a stale board is worse than a sparse one.

**What is automated.** Do not set these by hand.

- A new issue is added to the board with Status *Inbox*; a pull request that is ready for review
  (not a draft) is added as *In review* (`.github/workflows/project-status.yml`).
- Closing an issue, or merging a pull request that says `Closes #n`, sets *Done*; reopening sets
  *Backlog*. Do not move an item to *Done* yourself.
- Pull requests take no labels by hand, and `dependencies`, `python:uv`, `javascript` and
  `autorelease: …` belong to the bots.

**What you keep up to date.** Do each of these when its moment arrives.

| When | Do |
| --- | --- |
| You file an issue | Search for a duplicate first. Use an issue form so it has a type (Task, Bug or Feature); add every `area: …` label that applies, the themes that fit, and `needs spec` if it changes a fixed format. Set the milestone if it serves one (list them with the milestones API; do not invent one), and attach it as a sub-issue if it belongs under an umbrella. Write acceptance criteria someone else could check. |
| You find follow-up work | File it as a new issue and link it, and mark the place where something is left undone with the issue reference, as in the writing conventions below. Do not leave it in a comment. |
| You start work on an issue | Assign it to the person you are working for (never to yourself or a bot), set Status to *In progress*, and say in a comment what you are doing if the issue is not already clear. A person has at most two issues *In progress*. |
| You open a pull request | Put `Closes #n` in the body, so the issue closes on merge. Keep it a draft until it meets the definition of done; when it is marked ready, set the issue to *In review*. If the work has no issue, file one first. |
| The scope or understanding of an issue changes | Correct its labels, type, milestone and acceptance criteria, and comment on why. |
| Work is waiting on something outside the project | Add `blocked`, say in a comment what it waits on, and leave the issue in *Backlog*. Remove the label, and say so, when it is unblocked. |
| An issue will not be done, or is a duplicate | Close it as not planned (or duplicate) with a sentence saying why. Do not leave it in *Backlog*. |
| A pull request has merged | Check that the issue closed and, if its description was stale, correct it. File anything left over. |

**What people decide.** Do not set these unless the person you work for asks you to, and then do it
as they say: moving an issue from *Inbox* to *Backlog* or *Ready* (triage and refinement), the
*Iteration* (sprint planning) and *Size* (set by whoever moves it to *Ready*). When you think one
is wrong, say so in a comment on the issue, with your reasoning, instead of changing it.

**How to set things.** Issue type, labels, milestone, assignees and sub-issues are all settable with
the GitHub MCP tools (`issue_write`, `sub_issue_write`). Project fields such as Status are not
reachable from a cloud session: GraphQL and the organisation Projects endpoints are blocked there.
Where you have `gh` with the `project` scope (a local session), use `gh project item-edit`. Where
you cannot, do not pretend: put a line in the pull request description and in your final message
naming the issue and the Status it should move to (`Board: move #n to In progress`), so that a
person can do it in a click. Never report a board change as made unless you saw it made.

## Workflows

CI runs `zizmor` and `actionlint` over `.github/` (blanket policy, no unpinned actions). Pin every
`uses:` to a full commit SHA with the version as a trailing comment (`# v1.2.3`), and run
`uvx zizmor .github` before pushing any change to a workflow.

## Writing conventions

British English (`organisation`, `behaviour`, `licence` as noun). Declarative prose for a mixed
audience of researchers and engineers; no hype. Mark undecided matters with an explicit
`TODO(#123)` rather than filling in a plausible guess. The reference, directly after the word, is
the issue that will resolve it: open one if none fits, or list several, `TODO(#41, #57)`.
`scripts/check_todos.py` rejects a bare marker anywhere git tracks except `docs/blueprint/`,
and CI runs it.
